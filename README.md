# c64-lib-contract

A cross-consumer ABI / memory-manifest contract for Commodore 64 cryptographic libraries.

C64 crypto libraries (`c64-nist-curves`, `c64-x25519`, `c64-ChaCha20-Poly1305`, `c64-polyval`, future `c64-aes256-ecdsa`, ...) are consumed by multiple downstream projects (`c64-https`, `c64-wireguard`, future C64 TLS / IPsec / VPN clients). Without a shared contract, every consumer ends up patching library sources at integration time to fit its own memory layout, ZP, and REU usage — and every library tag bump forces consumer-side cfg surgery.

This repo specifies the contract that lets libraries publish their version, ZP slots, REU layout, segment names, and minimal-archive build targets as code, so consumers can ingest cleanly. Long-term goal: a library tag push automatically triggers a downstream `build → test → open PR` pipeline without any human cfg work.

## Status

**v0.14.1 (2026-08-28).** §8.2 clarification, from the clause meeting its first two implementations ([c64-x25519#116](https://github.com/JC-000/c64-x25519/pull/116), [c64-nist-curves#131](https://github.com/JC-000/c64-nist-curves/pull/131)): the read-once rule now names both conformant capture forms — `lda $DF00` keeps bit 5 (verify fault) available, `bit $DF00` is register-free at a hot site but discards it irrecoverably — and a non-normative note records that a settle met *structurally*, by unrelated intervening code, is conformant and is the easiest one to lose, since no emulator reproduces the failure. Previously **v0.14.0 (2026-08-28).** §13.2 allocates the fleet's first ip65 UDP error codes — `$46 NET_ERR_IP65_UDP_LISTEN`, `$47 NET_ERR_IP65_UDP_SEND` (ip65 range now `$41-$47`) — and adds a MUST that a backend **translate** its driver's native error values into its own family range rather than forward them: ip65's own `ip65_error` namespace (`$80-$A1`) sits entirely inside the contract's UCI range, so forwarding it would re-emit bytes this table has already given other meanings ([#148](https://github.com/JC-000/c64-lib-contract/issues/148)). Previously **v0.13.0 (2026-08-27).** §13.4 now requires adapters to start and verify the CIA TOD (measured: the reference bounded wait had been unbounded on hardware since it was written, #145); `$01 NET_ERR_TIMEBASE_STOPPED` is the first contract-generic error code; `$8D UCI_ERR_OPEN_REFUSED` allocated (UCI range now `$81-$8D`). Previously **v0.12.0 (2026-08-27).** §13.2 gains the cross-consumer error-code allocation table (ip65 `$41-$45`, UCI `$81-$8C` incl. c64-wireguard's `$8A`/`$8C`), §13.3 becomes firmware-agnostic (UDP backends publish `NET_UDP_SEND_MAX`/`NET_UDP_RECV_MAX` in a mandatory `net_caps.inc`; consumers derive MTU and assert buffers from it — the U64E 3.14d→3.15 move changed both ceilings under the draft), and §13.0 a canonical `net_families.inc`; c64-https is recorded as §13-aligned in §13.8. Previously: The [#76 restructuring](https://github.com/JC-000/c64-lib-contract/issues/76) is **complete**: §6 is the seven-clause build-and-consume chapter (defines-forwarding, `lib-app-owned`, per-variant manifests, the name surface with the §2 ZP prefix registry, footprint asserts, declared non-segment reservations), the document reads core (§1–§7) → domain (§8 crypto, §13 network) → meta, and every version through **v0.14.0** is tagged and citable — including the two zero-consumer carve-outs, which adopters can cite at `v0.11.0`. The five releases that had accumulated on `main` untagged (`v0.11.1`, `v0.12.0`, `v0.12.1`, `v0.13.0`, `v0.14.0`) were tagged 2026-08-28, each verified so that the tagged `SPEC.md` states its own version per §12's referencing rule, so §6.3's reject-or-invalidate rule is now pinnable at `v0.11.1` by the three libraries implementing it ([#71](https://github.com/JC-000/c64-lib-contract/issues/71) shape) and the whole §13 network-ABI arc is pinnable at `v0.12.0`–`v0.14.0` rather than only citable as `main`. Two much older tags do **not** satisfy that rule and were deliberately left alone rather than force-moved: `v0.3.0` and `v0.3.1` both point at commits whose `SPEC.md` calls itself 0.2.0 ([#150](https://github.com/JC-000/c64-lib-contract/issues/150)). **Five adopters**, at tags `c64-nist-curves` **v0.11.2**, `c64-x25519` **v0.11.2**, `c64-polyval` **v0.7.2**, `c64-ChaCha20-Poly1305` **v0.9.0**, `c64-mlkem` **v0.4.0** — see [adopters.md](adopters.md) for the per-section table and its per-release verification records, which are the authority on what has actually been checked at a ref. **`c64-mlkem` is the newest adopter** (registered v0.10.7) and the first library on both v0.11.0 zero-consumer carve-outs — born without the deprecated bare version exports and with `mlkem_`-prefixed archive members — so it is also the first walk of the §2 registry intake path, which had been described but never exercised. [consumers.md](consumers.md) carries the two integration rows; the composed `c64-https` pair links collision-free at tags, and a third consumer (`c64-e2ee-chat`) is in Phase 0 and not yet registered. [SPEC.md §12](SPEC.md#12-changelog) has the version history. Remaining before a v1.0 declaration: the §6.5 bare-name deprecation windows (which expire at each library's next MAJOR, and which a zero-consumer library now never enters) and the gate discussion on whether 1.0 precedes or follows those expiries.

## What's in here

- [**SPEC.md**](SPEC.md) — the contract itself: version equates, `.exportzp` ZP slots, REU bank symbols, segment naming, aggregate manifest equates, build-target conventions, shared-primitive promotion clauses.
- [**adopters.md**](adopters.md) — libraries that follow (or are in the process of following) the contract, with tracking-issue links per section.
- [**consumers.md**](consumers.md) — downstream projects that rely on the contract.
- [**precalc_table.inc**](precalc_table.inc) + [**examples/precalc_table_smoke.s**](examples/precalc_table_smoke.s) + [**Makefile**](Makefile) — canonical ca65 source for the SPEC §8.0 catch-loop `LIB_PRECALC_TABLE` macro, smoke-tested via `make verify` (requires `ca65` from the cc65 toolchain).

## How to participate

- **Library authors**: read SPEC.md, open a PR adding your library to `adopters.md`, file tracking issues against your library for each unimplemented section. Cross-link to this repo from your library's README so consumers can find the contract.
- **Consumer authors**: read SPEC.md, open a PR adding your project to `consumers.md`, link to your project's library-ingestion docs. If you need new contract sections (e.g., your consumer requires a property no current library exposes), open a PR against SPEC.md with the proposed addition + rationale.
- **Contract changes**: open a PR with the change + rationale. v1.0 will gate breaking changes behind a deprecation cycle (currently in draft, breaking changes are still cheap).
